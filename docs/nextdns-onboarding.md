# One-time NextDNS onboarding

Apply this procedure independently to `DNS`, then `DNS_WIFE`, `DNS_DIRECTOR` and `DNS_PV` after each environment's separate approval. Existing API credentials are sufficient; no interactive NextDNS website login is needed. Do not copy a journal between environments, even when hosts and API key are shared.

1. Keep `SYNC_ENABLED` absent or `false`. Run `Preview` for the selected environment on `main`, with `initialize=false`. It reads the API and creates an encrypted snapshot/plan; it cannot delete or add rules. Review the short summary and decrypt the detailed artifact locally with hidden key input.
2. Prepare an exact ID/name/IP/enabled list. Separate proven former automated rules from manual records and records whose origin cannot be proved. Include parent/subdomain conflicts, proposed new literal `www` names and OpenAI entries. Matching hosts is only a value check. Unknown IDs remain unmanaged unless the user explicitly decides to transfer those particular IDs into ownership despite unknown origin.
3. Obtain approval for the exact subset and its consequences. On the same code commit, dispatch `adopt` for **one** environment, supplying the successful Preview's `review_run_id` and exact `adopt_ids`. Set `initialize=true` only if this profile has no previous journal. This writes the journal only; it does not alter NextDNS rules. A profile with no legacy IDs can instead start ownership through a separately approved addition-only `apply`, `max_delete=0`, `initialize=true`; there is no implicit adoption.
4. Run another Preview. Verify the journal, all untouched manual records and proposed changes. Resolve unwanted `www`/OpenAI additions through separately reviewed `exact:` exclusions. Keep the new OpenAI permission off unless explicitly approved. Do not enable Sync while an oversized or forbidden plan remains unresolved.
5. With separate approval, perform any necessary initial API changes through reviewed `apply`; the first onboarding procedure itself authorizes no deletions. Check a fresh Preview and retain encrypted journal/backup copies.
6. Only after that control, approve setting this environment's `SYNC_ENABLED=true` and suitable limits. The defaults allow 20 additions, 20 updates and 20 DELETE requests, with at most 5% stale removals. Use a small approved test change to check Sync and the actual-result report, then restore the source through an approved follow-up. This is a rollout step, not performed by merging the code.
7. Ordinary operation is now: update hosts, run `Sync / ALL`, read the combined report. Environments still off are `Not onboarded`. A failing environment reports `Failed`; others continue. No review ID is required for permitted normal changes.

If a journal is missing/expired/corrupt, stop and restore a reviewed encrypted copy using the original key. Never reset ownership or re-adopt by domain/IP inference. After a partial failure, preserve the latest checkpoint artifact (including failed runs), inspect exact live IDs and rerun Preview before continuing. A POST with an ambiguous response may have created an unmanaged record; keep it until separately reviewed. See [recovery details](nextdns-safe-sync.md#failure-and-recovery).

For the audited DNS profile on 10 October 2026, all 770 candidate IDs match current hosts, but available logs/history do not prove who created those exact IDs. The confirmed-by-origin adopt list is therefore empty. The private excluded/candidate report records all 770 for an explicit ownership decision; this document grants no adoption. The journal currently owns no records. The other three environments have not been migrated by this work.
